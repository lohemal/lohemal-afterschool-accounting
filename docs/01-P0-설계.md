# P0 설계 — 프로젝트 기반과 자료 구조

작성 2026-10-13. 이 문서가 이 프로젝트의 **기준 문서**다. 뒤 단계에서 결정이 바뀌면 여기를 고친다.

## 1. 범위와 원칙

요구 문서(사용자 제공)의 6가지 원칙을 자료 구조가 **강제**하도록 설계했다.

| 원칙 | 어떻게 못 박았나 |
|---|---|
| 1 원본 보존 | 업로드 파일(`upload_file`)과 원본 행(`source_row`)은 거래와 분리해 보존. 취소·대체해도 지우지 않는다. |
| 2 거래 이력 | `ledger_entry` 한 줄에 학년도·귀속월·처리일·프로그램·학생·재원·항목·유형·금액·원본 참조·사유·등록 시각·대체 참조를 모두 둔다. |
| 3 소급 반영 | 귀속월(`fiscal_month_id`)과 처리일(`processed_on`)을 따로 둔다. 확정된 달에도 거래를 넣을 수 있고 `month_close` 이력은 남으며 화면에 '확정 후 변경'으로 표시한다. |
| 4 정정의 유연성 | 거래는 **덧붙이기만**. 트리거가 금액·분류 UPDATE 와 DELETE 를 막는다. 취소(void)·대체(replace)만 가능하고 `ledger_correction` 이 원 거래 ↔ 대체 거래를 잇는다. 구분 A(`input_error`)·B(`accounting_error`), B 는 후속 처리 완료(`completion`)를 따로 관리. |
| 5 중복 방지 | `upload_file(school_year_id, sha256)` 부분 유일 인덱스(취소·대체 제외). 같은 이름 재업로드는 `version_no` 로 판을 올린다. `source_row(upload_file_id, sheet, row)` 유일. |
| 6 금액 정확성 | 모든 금액 `INTEGER` + `CHECK(typeof(amount)='integer')`. Rust 는 `i64` 와 `checked_add` 만 쓴다. 재원 이동은 쌍의 합이 0 이어야 저장된다. |

## 2. 실제 엑셀 파일 분석 결과 (2026-10-13, 제공 파일 7개)

P1 에서 열 위치를 코드로 옮길 때 이 표를 기준으로 한다. 시트명·열은 **실측**이며 추측이 아니다.

| 파일 | 시트 | 머리글 행 | 열 |
|---|---|---|---|
| 수강생명단(방과후 통합 매니저 9월부터) | `수강생명단` | 1 | A 부서 · B 학년(문자) · C 반 · D 번호 · E 이름 · F 지원유형 · G 강사료 · H 수용비 · I 교재비 · J 재료비 · K 합계 · L 상태 · M 변경사유 |
| 강사료 내역 양식 | `강사료내역` (+ `Sheet1` 보조표) | 3 (1 제목, 2 기간) | A 순번 · B 부서 · C 강사명 · D 맞춤형지원 · E 3학년 지원금 · F 3학년 수익자 · G 수익자징수 · H 자유수강권 · I 최종강사료합계 · J 계좌 · K 은행. 마지막 `합계` 행(C열) |
| 교재,재료비 지급업체 | `2026.9.` (월마다 이름이 바뀜) | 3 | A 순번 · B 부서명 · C 수익자징수금액 · D 3학년 지원금 · E 3학년 수익자 · F 자유수강권 · G 최종지급금액 · H 업체명 · I 연락처 · J 메일. **B열 공란 행**(같은 부서의 둘째 업체, B 병합) 존재. `합계` 행 뒤에 교재비/재료비 총액 두 칸 |
| 수강생 명단2(1학기, 환불·추가징수) | `요약` · `부서별` · `학생별` | 2 (1행 2단 머리글: 징수/환불/추가징수/합계) | 부서별: A 순번 · B 부서 · C 학년 · D 반 · E 번호 · F 이름 · G~J 징수 · K~N 환불 · O~R 추가징수 · S~V 합계 (각 강사료·수용비·교재비·재료비) · W 비고 |
| 환불 및 추가징수 명단(1학기) | `환불` · `추가징수` | 1 | A 순번 · B 부서 · C 학년 · D 반 · E 번호 · F 이름 · G 강사료 · H 수용비 · I 교재비 · J 재료비 · K 합계 (· L 비고). 끝에 `합계` 행(F열) |
| 징수명단(기안용) | `전체` · `수익자` · `방과후이용권` · `자유수강권` | 3 | A 학년 · B 반 · C 번호 · D 이름 · E~I 강사료·수용비·교재비·재료비·합계, K~O 에 총계 블록. 이용권 시트는 이용권 5열 + 초과 5열 |
| 수강생 명단(1학기) | `학생명단` | 2 | B 부서 · C 학년 · D 반 · E 이름 · F 비고 (금액 없음 — 명부만) |

실측에서 확인한 사실

- 2학기 명단의 **지원유형** 값은 `일반` · `방과후 이용권` · `자유수강권` · `방과후 이용권 + 자유수강권` 네 가지. 상태는 `수강중` · `취소`.
- 부서 표기는 파일마다 다르다: 명단은 `코딩A`/`코딩B`(반 접미), 강사료·교재비는 `코딩`, `우쿨렐레&통기타`(두 부서 합산), `토탈공예미니어처1A`. → **프로그램 별칭 표(`program_alias`)** 가 필요하고 자동 추측은 하지 않는다.
- 금액 셀은 모두 정수(int). 소수 없음.
- 교재·재료비 파일은 교재비/재료비 합산이라 분리 불가 → 금액 항목 `textbook_material`(교재·재료비(합산))을 둔다.
- 강사료 파일 재원 열 = 맞춤형지원 · 초3 지원금 · 초3 수익자 · 수익자 · 자유수강권. 교재비 파일 = 수익자 · 초3 지원금 · 초3 수익자 · 자유수강권. 방과후이용권은 지출 파일에 열이 없다(수익자에 녹아 있을 가능성 — P2 에서 확인 필요).
- 제공된 파일의 학생 이름·번호는 비어 있거나 가명 처리되어 있다. 강사명·업체 연락처는 실제 값이므로 저장소에 넣지 않는다.

## 3. DB 구조 (스키마 v1, `src-tauri/migrations/001_init.sql`)

```
school_year 1─∞ fiscal_month 1─∞ ledger_entry ∞─1 program 1─∞ program_alias
     │                                 │  ∞─1 fund_type (parent_id 자기참조)
     │                                 │  ∞─1 amount_item
     │                                 │  ∞─0..1 student
     │                                 │  ∞─0..1 upload_file 1─∞ source_row (∞─0..1 ledger_entry)
     │                                 │  0..1 supersedes_id → ledger_entry (대체 사슬)
     │                                 └─1─∞ ledger_correction (entry ↔ replacement)
     ├─∞ program · student · upload_file
fiscal_month 1─∞ month_close
audit_log · app_setting
```

| 표 | 역할 | 핵심 제약 |
|---|---|---|
| `school_year` | 학년도 (3월~다음 해 2월) | `year` 유일, 현재 학년도 하나(부분 유일 인덱스) |
| `fiscal_month` | 회계월 12개 | `(year, ym)`·`(year, seq)` 유일, `status open/closed` |
| `fund_type` | 재원 유형 | 기본 7종 시드, `parent_id` 로 초3 수익자 부담금 → 수익자 |
| `amount_item` | 금액 항목 | 기본 6종 시드(교재·재료비 합산 포함) |
| `program` / `program_alias` | 프로그램과 파일별 표기 | 학년도 안에서 이름·별칭 유일 |
| `student` | 학생 식별 | `identity_key`(학년\|반\|번호\|이름) 유일 |
| `upload_file` | 업로드 파일·판 | sha256 살아 있는 것 유일, `status registered/previewed/applied/cancelled/replaced`, `replaced_by_id` |
| `source_row` | 원본 행(JSON 그대로) | `(file, sheet, row)` 유일 |
| `ledger_entry` | 회계 거래 | `amount` 정수 CHECK, `flow`×`entry_kind` 일관성 CHECK, 재원 이동은 `transfer_group_id` 필수, **UPDATE/DELETE 트리거 차단** |
| `ledger_correction` | 정정·취소 이력 | `action void/replace`, `category input_error/accounting_error`, `completion none/pending/done` |
| `month_close` | 월 확정·재개 이력 | 확정 시점 합계 JSON 스냅샷 |
| `audit_log` | 변경 이력(개인정보 없음) | |
| `app_setting` | 설정 | |

거래 유형(`entry_kind`): `initial_collect` 최초 징수 · `extra_collect` 추가징수 · `refund` 환불(음수) · `fund_transfer` 재원 이동(쌍) · `instructor_pay` 강사료 · `vendor_pay` 교재·재료비 · `adjustment` 정정.
흐름(`flow`): `collection` 징수 · `expenditure` 지출 · `transfer` 재원 이동. 단계(`stage`): `planned` 지급 예정 · `actual` 실제.

월별 합계는 저장하지 않는다. `repo::ledger::month_summary` 와 `repo::year::months` 가 `state='active'` 거래에서 매번 다시 계산한다.

## 5. 화면 (P0)

대시보드 · 월별 정산 · 자료 업로드 · 재원별 관리 · 차액 분석 · 변경 이력 · 설정.
미구현 기능은 노란 '준비 중 · P1~P5' 띠로 표시하고, 검증 열은 모두 '미검증'이다. 자료가 없으면 '자료 없음'을 보여 준다.
실제로 동작하는 것: 학년도 생성·현재 지정, 12개 월 띠와 월별 합계(거래가 있을 때), 재원·항목 이름 바꾸기·추가, 학교명, 변경 이력, 자료 폴더 열기.

## 6. 미결 질문 (P1 전에 확인)

1. 방과후이용권 재원이 강사료·교재비 지급 파일에서 어느 열에 들어가는가 (열이 없음).
2. `우쿨렐레&통기타` 처럼 두 부서가 합산된 강사료 행을 어느 프로그램에 귀속시킬지 (별칭 하나 → 프로그램 둘은 허용하지 않음. 사용자 분배 입력이 필요할 수 있음).
3. 1학기 `학생별` 시트는 부서 열이 없다 — 학생 단위 집계 전용으로만 쓸지.
4. 교재비 파일의 B열 공란 행: 바로 위 행과 B 병합이면 같은 부서로 보고, 병합이 없으면 '확인 필요'로 둘 것인지(요구 문서 3-4 규칙의 구체화).
