# P3 — 재원경정 · 환불 · 추가징수 · 회계 정정 거래

작성 2026-10-13. 앞선 문서: [01-P0-설계.md](01-P0-설계.md) · [02-P1-업로드와-되돌리기.md](02-P1-업로드와-되돌리기.md) · [03-P2-대조와-배분.md](03-P2-대조와-배분.md).

## 1. 세 가지 경제적 사건을 섞지 않는다

| 정정 | 뜻 | 원장(`ledger_entry`)에 남는 것 | 전체 징수 기준액 |
|---|---|---|---|
| 재원경정 `fund_transfer` | 재원의 변경 | `flow='transfer'` 쌍 (−A 출발 재원, +A 도착 재원, `transfer_group_id`) | 그대로 |
| 수강료 환불 `refund` | 징수 기준액 감소 (수강 취소·과오납) | `refund` 음수 징수 거래 | 감소 |
| 경정 반환 이행 `refund_return` | 재원경정 뒤 학부모에게 실제로 돌려준 사실 | **없음** — 경정이 이미 수익자 금액을 줄였으므로 다시 차감하면 중복 | 그대로 |
| 추가징수 `extra_collect` | 새 징수액 발생 | `extra_collect` 양수 징수 거래 | 증가 |

묶음은 `adjustment` 표(스키마 v5)에 남고 `adjustment_entry` 가 원장 거래를 잇는다. 묶음은 금액·분류를 고칠 수 없고(트리거) 지울 수 없다.
상태는 `planned`(처리 예정) → `done`(처리 완료) → `cancelled`(취소) 한 방향이고 `adjustment_status_log` 에 이력이 남는다.

- 처리 예정은 원장 거래의 `stage='planned'` 로 남아 **집계에서 빠진다**(대조 엔진은 `stage='actual'` 만 센다). 완료로 바꾸면 `stage='actual'`·처리일이 채워진다.
- 취소는 원장 거래를 `void`(재원경정은 쌍을 함께)하고 묶음을 cancelled 로 둔다. 사유 필수. 취소된 묶음은 다시 취소할 수 없다.
- 재원경정에 연결된 반환 이행이 살아 있으면 경정을 먼저 취소할 수 없다(반환 이행부터).

## 2. 검증 규칙 (`repo::adjustment::preview`)

- 금액 > 0 · 사유 필수 · 처리 완료면 처리일 필수 · 귀속월이 학년도에 속해야 함 · 확정된 달은 차단(자동 재개 없음).
- 재원경정: 출발 ≠ 도착(통합된 재원은 같은 재원), **출발 재원의 현재 기준액 ≥ 경정 금액**(음수 잔액 차단, 예외는 별도 절차), 같은 학생·프로그램·귀속월·재원·금액의 경정이 살아 있으면 중복 차단. 등록 직후 쌍의 합이 0 인지 검산한다.
- 수강료 환불: 환불 가능 금액 = 현재 재원 기준액(최초 징수 + 추가징수 + 기존 환불 + 재원경정 + 배분 귀속, 실제 처리분) − 처리 예정 환불. 초과 차단. 누적 환불을 함께 보여 준다.
- 반환 이행: 근거 재원경정이 필요하고, 반환 누계가 경정 금액을 넘지 못한다.
- 환불·추가징수의 중복: 같은 학생·프로그램·귀속월·항목·금액의 살아 있는 거래(엑셀 업로드 포함)가 있으면 목록으로 보여 주고, '중복 아님 확인'을 켜야 등록된다(금액만 같다는 이유로 무조건 막지 않는다).
- 관련 원본 거래를 고르면 살아 있고 같은 귀속월·프로그램인지 확인한다.
- 학생을 고르지 않으면 프로그램 단위(`scope='program'`)로 등록되며 화면에 그렇게 표시된다.

재원 기준액은 `FundIndex` 로 통합 재원을 푼 id 기준이며, 배분으로 귀속된 미배분 거래도 포함한다.

## 3. 귀속월과 처리일

원장 거래의 `fiscal_month_id`(귀속월)와 `processed_on`(처리일)은 다른 칸이다. 4월 수강료 50,000 중 20,000 을 9월 15일에 환불하면
거래는 4월에 귀속되고 처리일은 9월 15일이다. 4월 귀속월 기준액은 30,000 이 되고, 9월 기준액은 변하지 않는다.
정정 이력 화면은 귀속월 기준과 처리일 기간 기준 두 가지로 조회한다(시험 `b_refund_planned_then_done_then_cancel_and_retroactive_view`).

## 4. 대조 엔진 연동

- `recon::load_entries` 가 `transfer` 흐름도 읽어 재원별 기준액에 반영한다(쌍의 합이 0 이라 전체 기준액은 같다). 행에 `transfer_count` 와 단서가 붙는다.
- 재원경정·환불·추가징수가 완료되면 재원별·프로그램별 차액이 바로 다시 계산되고, 확인 메모의 지문이 달라져 **재확인 필요**가 뜬다(메모 보존).
- 관련 원본 거래가 파일 취소·교체로 취소되면 묶음은 `orphan`(원본 재확인 필요)으로 표시되고, 그 거래가 섞인 행은 `원본 재확인 필요` 상태가 되어 정상으로 계산되지 않는다. 정정 거래 자체는 지우지 않는다. 복원은 새 거래를 만들므로 옛 원본 id 는 계속 취소 상태이고, 담당자가 정정을 다시 확인한다.

## 5. 차액 분석 연동

차액 상세에서 재원별 불일치가 있으면 **[재원경정 등록…]** 단추가 나타나 회계 정정 화면의 재원경정 탭으로 이동한다. 귀속월·프로그램·항목은
채워지고 재원별 차액은 후보로만 보인다. 방향과 금액은 담당자가 입력하고 미리보기(경정 전·변동·후)를 확인한 뒤 등록한다. 자동 실행은 없다.

## 6. 시나리오 계산 결과 (가명 시험)

| 시나리오 | 결과 |
|---|---|
| 1. 일반 수익자 30,000 → 자유수강권 | 경정 전 일반 100,000 / 자유 50,000 (합 150,000) → 경정 후 70,000 / 80,000 (합 150,000). 원장 징수 합계 150,000 · 재원 이동 잔액 0 |
| 2. 4월 50,000 중 20,000 을 9월 15일 소급 환불 | 4월 귀속월 기준액 50,000 → 30,000, 9월 기준액 50,000 그대로. 처리일 9월 조회에 '4월 (2026-04)' 귀속 환불 20,000 이 보임 |
| 3. 30,000 경정 뒤 반환 이행 30,000 | 경정 후 일반 0 / 자유 30,000, 전체 30,000. 반환 이행 등록 뒤에도 전체 30,000 · 일반 0 / 자유 30,000 (원장 거래 0건) → 중복 차감 없음 |

## 7. 실제 9월 자료 연동 (로컬 전용)

시나리오 2(통합 매니저 명단 기준)의 바둑 교재·재료비는 '총액 일치 · 재원 불일치'(일반 수익자 −12,000 · 이용권 +12,000)였다.
담당자가 방과후이용권 12,000 → 일반 수익자로 경정하는 흐름을 시험으로 돌렸다(프로그램 단위, 실제 결정은 원본 회계자료로 해야 한다).

| | 경정 전 | 변동 | 경정 후 |
|---|---:|---:|---:|
| 방과후이용권 | 72,000 | −12,000 | 60,000 |
| 일반 수익자 | 360,000 | +12,000 | 372,000 |
| 전체 기준액 | 432,000 | 0 | 432,000 |

경정 후 상태 `정상 (초3 초과금 제외)` · 단순 차액 −12,000(초3 초과금 지급 12,000 은 여전히 비교 제외) · 대조 차액 0 · 재원경정 2건.
실사용 DB 가 아닌 메모리 DB 에서만 실행했다.

## 8. 남은 제한 · P4 전 확인

- 음수 잔액 예외(기준액보다 큰 경정)는 차단만 한다. 실제 업무에 필요한 예외가 확인되면 별도 승인 절차를 설계한다.
- 재원 간 이동 허용 정책(어떤 재원 → 어떤 재원이 회계상 허용되는지)은 아직 모두 허용이다. 정책 표로 분리할 자리는 `preview` 한 곳이다.
- 확정월 소급 정정은 차단만 한다(재개 → 등록 → 재확정). 정책이 바뀌면 `guard_month` 한 곳을 고친다.
- 파일 복원 뒤 orphan 표시는 담당자가 정정을 취소하고 새 원본 거래에 다시 등록하는 방식이다. 자동 재연결은 하지 않는다.
