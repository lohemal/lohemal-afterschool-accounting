# P5 — 운영 안정화 · 백업과 복원 · 무결성 검사 · 내보내기

작성 2026-10-13. 앞선 문서: [01-P0-설계.md](01-P0-설계.md) · [02-P1-업로드와-되돌리기.md](02-P1-업로드와-되돌리기.md) · [03-P2-대조와-배분.md](03-P2-대조와-배분.md) · [04-P3-회계-정정.md](04-P3-회계-정정.md) · [05-P4-자유수강권.md](05-P4-자유수강권.md).

## 1. 원칙

- **백업은 만든 뒤 검증한다.** 검증을 통과한 백업만 정상 목록에 보이고 복원에 쓸 수 있다.
- **복원은 고르기 → 검증 → 비교·미리보기 → 최종 확인('복원' 입력) → 안전 백업 → 임시 준비·검증 → 전환 → 복원 후 검증** 순서다. 어느 단계에서 실패해도 기존 자료가 남는다.
- **무결성 검사는 아무것도 고치지 않는다.** 오류·확인 필요를 원인·확인 방법·수정 안내와 함께 보여 준다.
- 방과후이용권 **대상 여부(기록)와 사용 실적(원장)을 분리**한다. 실적이 있다는 이유로 대상자를 자동 확정하지 않는다.
- **합산 항목의 중복 계산을 막는다.** 확인되기 전까지 지원액 계산·일괄 경정에서 뺀다. 원장은 바꾸지 않는다.
- 학기 공백 달은 담당자가 **명시적으로 확인**해야 정책이 저장된다.

## 2. 백업 (`ops::backup`)

- 실행 중 DB 파일을 복사하지 않는다(WAL 에만 있는 내용을 놓친다). `rusqlite::backup::Backup`(SQLite Online Backup API)으로 일관된 스냅샷을 임시 파일에 뜬다.
- 패키지(zip) = `manifest.json` + `asaccounting.db` + `uploads/<sha256>.<ext>…`(보관 중인 원본 엑셀). manifest 에 생성일·앱 버전·스키마 버전·형식 버전(1)·학년도·종류·파일별 SHA-256·크기·전체 해시(`package_sha256`)·주요 표 건수가 들어간다. 보관 폴더에 없는 원본은 `missing_files` 로 적고 `complete=false`(완전한 백업이 아님)로 표시한다.
- 검증(`verify`): 패키지 구조 → manifest 형식 → 파일별 체크섬·크기 → 전체 해시 → DB 를 꺼내 `integrity_check`·`foreign_key_check`·주요 표 접근·스키마 버전·건수가 manifest 와 같은지. 결과는 곁 파일 `<zip>.verify.json` 에 남고 작업 이력에 기록된다.
- 종류: 수동(`manual`) · 자동(`auto`, 프로그램 시작 때 하루 한 번) · 마이그레이션 직전(`migration`, `migrate::run` 이 패키지로 만든다) · 복원 직전(`pre_restore`). 자동 백업만 최근 N개(기본 10, 설정 `backup.keep`)를 남기고 정리하며 나머지 종류는 지우지 않는다. 정리 내역은 작업 이력에 남는다.
- 파일명 `방과후회계백업_YYYYMMDD_HHMMSS_<종류>.zip`, 폴더 `<자료 폴더>/backups/`. 이전 형식(.db 단일 파일)은 목록에 '이전 형식' 으로만 보이고 복원에 쓰지 않는다.
- 백그라운드 상주·작업 스케줄러는 만들지 않았다(지시서).

## 3. 복원 (`ops::restore`)

- 미리보기(`inspect`): 검증 결과, manifest, 현재 자료와 백업 자료의 건수 비교(스키마·원장·정정·환불·대상자·묶음·업로드·학생·월 확정·감사 로그), 차단 사유(검증 실패·미지원 형식·앱보다 새로운 스키마), 경고(원본 없음·백업 이후 자료 사라짐).
- 실행(`apply`): `confirm` 없이는 아무것도 하지 않는다. ① 복원 직전 안전 백업을 만들고 검증(실패하면 중단) ② 임시 폴더에 DB 를 꺼내 `integrity_check` ③ `Db::with_file_swap` 으로 잠금을 쥔 채 연결을 닫고(WAL 체크포인트) 현재 파일을 `.before-restore` 로 옮긴 뒤 새 파일을 놓고 원본 엑셀을 보관 폴더에 꺼낸다(같은 이름은 건너뜀) ④ 다시 열어 마이그레이션(오래된 스키마면 갱신)과 `integrity_check`·외래키 검사 ⑤ 실패하면 `.before-restore` 를 되돌려 다시 연다. 잠금을 쥐고 있는 동안 다른 읽기·쓰기는 기다린다.
- 전체 복원만 한다. 부분 복원(학생·월·프로그램)은 원장·정정·환불·감사 연결을 깨뜨릴 수 있어 만들지 않았다.
- 이력: 자료 폴더의 `ops-history.jsonl`(DB 밖, 덧붙이기만)에 복원 시각·파일·복원 전/후 DB 식별(DB 파일 SHA-256)·결과·안전 백업·실패 사유가 남는다. 과거 DB 를 복원해도 사라지지 않는다. 성공하면 복원된 DB 의 감사 로그에도 `ops.restore` 한 줄이 남는다.
- 시험은 `apply_inner(.., fail_at)` 로 파일 이동 뒤·복사 뒤(깨진 파일)·검증 뒤 세 지점에서 일부러 실패시켜 기존 DB 유지와 실패 이력을 확인한다.

## 5. 방과후이용권 대상 여부 (스키마 v8 `after_voucher_target`)

학생별 상태 미확인·대상자·비대상자·지원 종료, 적용 시작·종료일, 대상 확인일, 확인 근거(대상자 확정 때 필수), 변경 사유(상태 변경 때 필수). 변경은 `after_voucher_target_log` 에 남는다. 목록에는 기록이 없어도 이용권 실적이 있는 학생이 '기록 없음 · 확인 필요' 로 보인다(자동 생성은 하지 않는다).
자유수강권 계산의 중복 대상자(`dual`) = 대상자로 확인됨 **또는** 이용권 실적 있음. 실적은 있는데 대상 확인이 없으면 안내 문구와 함께 일반 수익자 금액은 '재원 확인 필요' 로 남는다. 대상자로 확인되면 실적이 0원이어도 초3 초과금 우선 규칙이 적용된다(시나리오 7).

## 6. 합산 항목 중복

같은 달·프로그램(학생)에 '교재·재료비(합산)' 과 개별 교재비/재료비 징수가 함께 있으면 그 칸들은 `dup_check`(합산 항목 중복 여부 확인 필요)로 표시되고 지원액 계산·일괄 경정 제안에서 빠진다. 무결성 검사도 같은 항목을 '확인 필요' 로 낸다. 원장은 바꾸지 않으며, 합산이 표시용이면 지원 대상 항목에서 합산을 빼거나 파일을 교체한다. 개별 항목이 없는 독립 합산은 그대로 계산된다(시나리오 6: 강사료 30,000 + 재료비 10,000 + 합산 40,000 → 80,000 으로 계산하지 않고 30,000 만, 경정 제안 1건).

## 7. 학기 공백 명시 확인

정책 미리보기가 공백 달을 찾으면 "설정된 학기 기간에 포함되지 않는 8월 (2026-08) 은(는) 자유수강권 지원액이 0원으로 계산됩니다. 이 설정을 유지하시겠습니까?" 를 보여 주고, `confirm_gap`(화면의 '공백 기간 확인' 체크) 없이는 저장을 막는다. 확인하고 저장하면 `voucher_policy.gap_confirmed=1` 로 이력에 남는다. 기존 완료 거래는 바뀌지 않는다.

## 11. 남은 제한

- 자동 백업은 프로그램 시작 시점 기준 하루 한 번이다. 상주 프로그램·작업 스케줄러는 없다.
- 복원은 전체 복원만. 백업에 없던 원본 파일은 복원 뒤 '원본 없음' 으로 남는다.
- 백업·내보내기 파일에는 학생 개인정보가 들어 있다. 저장 위치와 반출은 담당자가 관리한다.
- 합산 항목의 중복 판정은 같은 달·프로그램에 합산과 개별 항목이 공존하는지만 본다. 원본 파일 구조를 자동으로 해석하지 않는다.
