# P4 — 자유수강권 관리 (대상자 · 한도 · 사용액 · 소급 경정 · 환불 · 전입생)

작성 2026-10-13 · P4.1 보완 2026-10-13 (10장). 앞선 문서: [01-P0-설계.md](01-P0-설계.md) · [02-P1-업로드와-되돌리기.md](02-P1-업로드와-되돌리기.md) · [03-P2-대조와-배분.md](03-P2-대조와-배분.md) · [04-P3-회계-정정.md](04-P3-회계-정정.md).

## 1. 원칙

- **원장에 새 표를 쓰지 않는다.** 자유수강권 때문에 생기는 모든 회계 사건은 P3 `repo::adjustment` 로만 등록한다 — 소급·당월 지원은 **재원경정**(수익자 → 자유수강권, 원장 transfer 쌍, 전체 기준액 불변), 환불은 **경정 반환 이행**(refund_return, 원장 거래 없음 — 경정이 이미 수익자 금액을 줄였다).
- **사용액·잔액은 저장하지 않는다.** 원장(살아 있고 실제 처리된 징수·재원경정 + 배분 귀속)에서 그때그때 계산한다.
- **지원액은 자동으로 확정되지 않는다.** 미리보기 → 담당자가 행을 고름 → 승인 묶음 등록. 등록 직전에 다시 계산·검증하고, 한 건이라도 막히면 **전부 되돌린다**(조용히 건너뛰지 않음).
- **환불은 자동으로 완료되지 않는다.** 처리 완료에는 '실제 수납 확인' + 수납 근거 + 처리일이 필요하다. 처리 예정은 근거 없이 등록된다.
- **한도 초과분은 지원하지 않는다.** 계산 지원액보다 실제 자유수강권 사용액이 많으면 '확인 대상'으로만 보여 주고 되돌리지 않는다.
- **전입생의 이전 학교 사용액은 확인 전까지 '확인 필요'** 이고 사용액 계산이 막힌다. 0원도 담당자가 명시해야 확인된다.
- 대상자 파일 업로드는 실제 양식이 확인되기 전까지 만들지 않는다. 학생을 골라 직접 등록한다(명단에 없는 전입생은 학년·반·번호·이름으로 직접 등록 — 네 가지가 같으면 같은 학생).

## 2. 자료 구조 (스키마 v6, `006_voucher.sql`)

| 표 | 뜻 | 바뀌는 방식 |
|---|---|---|
| `voucher_policy` | 학년도 지원 한도 정책 — `annual`(연간) · `semester`(1·2학기, `carry_over` 이월) · `unlimited` | 바꾸면 이전 행 `superseded_at` 닫고 새 행 (이력) |
| `voucher_exception` | 학생별 예외 한도 (같은 구조 + 사유) | 같은 방식, 해제는 닫기만 |
| `voucher_target` | 대상자 (학생당 한 행). 상태 `pending`(확인 전) · `confirmed`(확정) · `ended`(지원 종료) · `cancelled`(대상 취소), 확정일·적용 시작/종료일, 전입 여부·전입일, 이전 학교 사용액·확인 상태 | UPDATE 허용, 모든 변경은 `voucher_target_log` 에 남음, DELETE 금지 |
| `voucher_batch` · `voucher_batch_item` | 승인 묶음과 그 안의 `adjustment` 연결 | 불변 · 삭제 금지 |
| `voucher_refund` | 반환 이행(`adjustment` refund_return)에 붙는 수납 확인·근거 | 연결 불변, 수납 확인·근거만 채워짐 |

## 3. 사용액 계산 (`domain::voucher::plan`, DB 의존 없음)

- 입력: 한도, 이전 학교 사용액(전입 달 차례), 적용 기간(회계월 차례, 양 끝 포함), 달·프로그램·항목별 **지원 대상 수강료**, 담당자 배분(선택).
- **지원 대상 수강료 = 자유수강권 + 수익자 계열(일반 수익자·초3 초과금)**. 맞춤형지원·방과후이용권 등 다른 지원 재원이 낸 몫은 한도를 쓰지 않고 자유수강권으로 바꾸지도 않는다.
- 달 순서대로 `MIN(지원 대상 수강료, 남은 한도)`. 한도가 바닥나면 그 뒤는 0 (수익자 전환, `exhausted_seq`).
- 한 달에 **여러 프로그램**이 있고 한도가 모자라면 `needs_decision` — 자료에 수강 시작일이 없어 자동으로 정하지 않는다. 담당자가 프로그램별 배분(합 = 남은 한도, 각 ≤ 수강료)을 주면 그대로 쓴다. 한 프로그램에 항목이 여럿이면 항목 순서대로 채운다.
- 학기별: 1학기 = 3~8월(차례 1~6), 2학기 = 9~2월. 이월은 적용 기간이 1학기에 걸쳐 있을 때만 1학기 잔액을 2학기에 더한다. 이전 학교 사용액은 연간이면 연간에서, 학기별이면 전입 학기에서 뺀다.
- 불변식: 수강료 = 자유수강권 + 수익자 + 기타 재원 (실제 재원 구성은 `repo::voucher::usage` 가 원장에서 셈).

`repo::voucher::usage` 는 칸마다 실제(자유·수익자·기타)와 계산 지원액을 나란히 놓고 `delta = 계산 − 실제 − 처리 예정 경정` 으로 상태를 낸다:
`ok`(일치) · `retro`(경정 필요, delta > 0) · `over`(확인 대상, delta < 0 — 자동 되돌림 없음) · `decide`(배분 결정 필요) · `pending`(처리 예정 경정 있음) · `outside`(적용 기간 밖).

## 4. 소급 지원 계산 · 승인 묶음 (`retro_preview` · `apply`)

- 제안 = `retro` 칸마다 수익자 계열 재원(정렬 순)에서 delta 만큼 → 자유수강권 재원경정. 각 제안을 P3 `adjustment::preview` 로 검사해 확정월·중복·음수 잔액이면 `blocked`. 수익자 부담분이 모자라면 `short`(다른 지원 재원은 바꾸지 않음).
- 이미 자유수강권인 금액은 빠지고(실제), 처리 예정으로 등록된 경정은 `pending` 으로 빠진다 → 중복 경정 없음. 같은 제안을 두 번 등록하면 P3 중복 검사가 막는다.
- `apply` 는 묶음 안 학생마다 사용액을 **다시 계산**해 행이 `retro` 이고 금액 합 ≤ delta, 변경 전 재원이 수익자 계열이며 그 재원 기준액 이하인지 본 뒤 `adjustment::create`(fund_transfer) 로 등록한다. 어느 단계든 실패하면 트랜잭션 전체가 되돌아간다. 등록 뒤 묶음 합 = 경정 합, 원장 쌍 합 = 0 을 검산한다.
- 처리 예정(`planned`)으로 등록하면 집계에서 빠지고, 완료·취소는 회계 정정 → 정정 이력에서 한다(P3 규칙 그대로).

## 5. 환불 (`refund_list` · `refund_register` · `refund_complete`)

- 환불 대상 = 학생 단위 **수익자 계열 → 자유수강권** 재원경정 전부(묶음에서 온 것과 직접 등록한 것 모두). 프로그램 단위 경정은 제외.
- 상태: `none`(미처리) · `planned`(처리 예정) · `partial`(일부 완료) · `complete`(처리 완료, 완료 누계 ≥ 경정 금액) · `cancelled`(경정 취소). 반환 누계가 경정 금액을 넘으면 P3 가 막는다.
- 처리 완료 등록·완료 처리에는 `collected_confirmed` + 근거 + 처리일이 필수. 근거 재원경정이 처리 완료가 아니면 환불을 등록하지 않는다.
- 환불 취소는 P3 `adjustment::cancel`. 살아 있는 환불이 있으면 경정을 먼저 취소할 수 없다.

## 6. 대조 엔진 연동

- 승인 묶음이 등록되면 월별 정산·차액 분석이 다시 계산되고(재원경정 쌍 반영) 기존 확인 메모는 지문이 달라져 **재확인 필요**로 표시된다(메모 보존).
- 정상인데 비교 제외 재원이 있는 행의 라벨을 **"비교 가능 재원 정상 · 초3 초과금 미검증"** 꼴로 바꿨다(불일치는 "불일치 (… 제외)" 그대로).
- 원본 징수 거래가 취소되면 경정 쌍만 남아 사용액 현황에 `over`(확인 대상)로 드러나고, 묶음·환불 대상은 그대로 남아 담당자가 확인한다. 자동 재연결·자동 취소는 없다.

## 8. 실제 9월 자료 연동 (로컬 전용)

실제 파일은 학생 식별 정보가 비어 있어 학생 단위 대상자를 만들 수 없다. `real_september_recon` 에서 정책 등록·대상자 0명·제안 0건·환불 대상 0건(프로그램 단위 바둑 경정은 섞이지 않음)·대조 결과 불변을 확인했다. 바둑 교재·재료비 경정 후 라벨은 "비교 가능 재원 정상 · 초3 초과금 미검증".

## 9. 남은 제한 · P5 전 확인

- 지원 대상 항목: 강사료·수용비·교재비 등 모든 징수 항목을 대상으로 본다. 특정 항목을 빼는 정책이 확인되면 `usage` 의 charges 한 곳을 고친다.
- 같은 달 여러 프로그램의 배분 기준(수강 시작일 등)이 자료에 들어오면 엔진의 기본 순서를 바꿀 자리는 `domain::voucher::plan` 의 `needs` 분기 한 곳이다.
- 대상자 파일 양식이 확인되면 업로드 파서를 더한다(지금은 수동 등록만).
- 환불 수납 근거는 메모 문자열이다. 수납 파일 연결이 필요하면 `voucher_refund` 에 `upload_file_id` 를 더한다.

## 10. P4.1 보완 — 방과후이용권 중복 대상자 · 초3 초과금 우선 · 학기 기간 · 지원 대상 항목

### 10-1. 재원 우선순위
- 재원 관계는 id 로 푼다(`FundIndex`): 방과후이용권(초3 지원금이 통합됨)은 독립 뿌리, 초3 초과금은 일반 수익자(수익자 뿌리)의 하위, 자유수강권은 독립. 학년 정보로 판단하지 않는다.
- **지원 대상 수강료 = 자유수강권 + 초3 초과금 + 일반 수익자.** 방과후이용권·맞춤형지원 등 다른 지원 재원이 낸 몫은 한도를 쓰지 않고 자유수강권으로 바꾸지도 않는다(방과후이용권 지원액 불변, 자유수강권 사용액에 포함하지 않음).
- 전환 순서: **① 방과후이용권 유지 → ② 초3 초과금 → ③ 일반 수익자.** 한도가 모자라면 초3 초과금만큼만 바꾸고 나머지는 **원래 재원으로 유지**한다(초3 초과금을 일반 수익자로 바꾸지 않는다). 칸마다 `retro_g3x`·`retro_general` 로 나눠 보여 준다.
- 이용권 실적이 있는 학생(`dual`)의 일반 수익자 금액은 제안이 **`check`(재원 확인 필요)** 로 나오고, 담당자가 '재원 확인'을 켠 행(`confirmed`)만 등록된다. 초3 초과금을 다 쓰기 전에 일반 수익자를 등록하면 우선순위 위반으로 묶음 전체가 되돌아간다.
- 제한 없음은 "한도 검사 없이 지원 대상 금액을 자유수강권으로"라는 뜻이다. 수익자 계열 금액이 남아 있으면 제안이 나온다(P4 보고의 제안 0건은 이미 모두 자유수강권이었던 경우).

### 10-2. 초3 초과금 소급 환불
초3 초과금 → 자유수강권 경정(P3 fund_transfer)이 환불 대상이 되고, 환불은 P3 반환 이행(원장 거래 없음)으로 남는다. 환불 목록은 기존 재원(초3 초과금 환불 / 일반 수익자 환불)을 구분해 보여 주고 재원으로 거를 수 있다. 완료는 실제 수납 확인·근거·처리일이 있어야 하며(미납이면 완료 불가), 반환 누계가 경정 금액을 넘으면 막힌다. 살아 있는 환불이 있는 경정은 먼저 취소할 수 없다.

### 10-3. 학기 기간 (스키마 v7)
`voucher_policy` 에 학기 시작·종료일 네 칸을 더했다. NULL 이면 기본값(1학기 3/1~8/31 · 2학기 9/1~다음 해 2월 말)으로 읽으므로 v6 정책은 계산 결과가 바뀌지 않는다. 검증: 형식 · 시작 ≤ 종료 · 두 학기 겹침 금지 · 학년도 범위 · 한도 음수 금지. 학기 사이 공백 달은 **미지원 기간**(어느 학기에도 넣지 않고 지원액 0, 안내 문구)으로 저장 전 미리보기에 경고한다. 이월은 적용 기간이 1학기 달을 포함할 때만 1학기 잔액을 2학기에 더하고 근거를 `notes` 로 보여 준다. 정책을 바꿔도 완료된 경정은 그대로이고 과거 정책 판의 학기·항목 기준은 이력에서 확인한다.

### 10-4. 지원 대상 항목
`voucher_policy_item`(정책 판 × 금액 항목, 불변). 행이 없으면 모든 항목 지원(P4 호환). 지원 대상이 아닌 항목의 칸은 `excluded` 로 표시되고 계산·제안에서 빠지며 기존 재원으로 남는다. 저장 전 미리보기(`policy_preview`)가 지원 대상에서 빠지는 항목에 이미 등록된 자유수강권 경정 건수·금액을 보여 주고, 완료된 경정은 자동으로 취소·수정하지 않는다.

### 10-5. 여러 프로그램
재원 우선순위(초3 초과금 → 일반)와 프로그램 배분 순서는 다른 개념이다. 같은 달 여러 프로그램에 한도가 모자라면 여전히 담당자 배분이 필요하고(합 = 남은 한도, 각 ≤ 지원 대상 금액), 배분 뒤 제안은 칸마다 다시 초3 초과금부터 나온다.
